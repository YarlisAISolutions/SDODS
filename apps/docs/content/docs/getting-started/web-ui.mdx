## Start it

The command depends on how SDODS got onto the machine, not on your operating system — the CLI is
identical on macOS, Linux and Windows.

<Tabs items={['Installed', 'From a clone', 'Docker']}>
<Tab value="Installed">
```bash
sdods users create --admin --username admin --password '<at least 8 chars>'
sdods serve --open
```

The UI is at `http://127.0.0.1:4444`. `--open` launches your browser. On Windows the same commands
work in PowerShell and in `cmd`; inside WSL, use the Linux form rather than the PowerShell one.

</Tab>
<Tab value="From a clone">
```bash
bun run web:build                   # once: the UI bundle is not committed
bun run sdods users create --admin --username admin --password '<at least 8 chars>'
bun run sdods serve --open
```

`web:build` is not optional. `packages/web/dist/` is gitignored, so a fresh clone has no bundle and
the server answers with a short page saying the UI is unavailable instead of the app.

Use `bun run sdods` rather than a globally installed `sdods` inside a checkout: the two drift, and
because both report the same version the mismatch is confusing when it surfaces.

</Tab>
<Tab value="Docker">
```bash
docker run --rm -p 8080:8080 -v sdods-data:/data ghcr.io/yarlisaisolutions/sdods-server
```

Note the port: the image binds `0.0.0.0:8080`, not 4444. On Apple silicon add
`--platform linux/amd64` — the published image is amd64 only, and Docker refuses the pull rather
than emulating.

</Tab>
</Tabs>

## The first user

On a database with no users, `serve` prints a one-time setup URL:

```text
ℹ First run: create the admin at http://127.0.0.1:4444/setup?token=<token> (or: sdods users create --admin --username <name> --password <pw>)
```

Open it and fill the form, or use `sdods users create` — whichever suits. The browser path is the
one to hand someone who should never touch a terminal. If you lose the token, restart `serve` to
print a new one, or paste it into the field on `/setup`.

`--admin` makes a platform admin and owner of every organization without one. Add more people with
`--role viewer|editor|admin`, and scope them with
`sdods users grant <username> --workspace <slug> --role editor`.

<Callout type="warn">
  Run `users create` and `serve` from the same workspace root. The platform database is
  `<workspace>/.sdods/sdods.db`, and each command walks up from the current directory to find the
  workspace. Run them in different places and you create the admin in one database while the server
  reads another — the sign-in then fails with entirely correct credentials. `SQLITE_PATH` pins both
  to one file if you want to be certain.
</Callout>

Signing out clears the session on the server and every cached query in the browser, so nothing
from one session is readable in the next on a shared machine. If a session ends while the app is
open — it expires, an admin runs `sdods users deactivate`, or a token is revoked — the next request
returns you to the sign-in form rather than leaving a half-loaded page behind.

## If it does not start

| Symptom                                      | Cause                                                                              | Fix                                                      |
| -------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `Port 4444 is already in use`                | another `serve`, or the desktop app                                                | `sdods serve --port 4445`                                |
| A page saying the web UI is unavailable      | a clone with no built bundle                                                       | `bun run web:build`, then restart                        |
| Sign-in fails with the right password        | two different `.sdods/sdods.db` files                                              | run both commands from one workspace root                |
| An unexplained `TypeError` from a dependency | Node older than 22                                                                 | `node -v`, then `nvm use 22` or `fnm use 22`             |
| `sdods: command not found` after installing  | a version manager owns Node, and the global install belongs to a different version | re-install, or use the installer's bun path              |
| Forgot the admin password                    | no other admin can reset it from the Users page                                    | `sdods users set-password <username> --password '<new>'` |
| `/setup` says the setup token is invalid     | the token is minted when `serve` starts, and users were removed after that         | restart `serve` and use the new link                     |

`sdods doctor` reports Node, bun, browsers, projects, environment variables and the database in one
pass.

The server is a Fastify application. It spawns the same `sdods` commands you run by hand and streams their logs over Server-Sent Events, so a run started from a browser looks exactly like one started from a terminal.

## Reinstall or reset

Three levels, from the lightest to a clean machine. Stop `sdods serve` first, and run every command
from the workspace root — the same rule as creating the first user.

| Level         | Keeps                                      | Removes                                                      | Command                                     |
| ------------- | ------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------- |
| Users reset   | projects, runs, schedules, organizations   | every user, session, API token and membership                | `sdods users reset --yes`                   |
| Factory reset | your project files (features, steps, envs) | the whole platform database: users, runs, schedules, history | `sdods db reset --yes`, or delete `.sdods/` |
| Reinstall     | your workspaces                            | the `sdods` command itself                                   | uninstall, then install                     |

After a users reset or a factory reset, start `serve` again: with no users it prints a new one-time
`/setup` link, exactly as on the first run. To keep a copy of the database before a factory reset,
run `sdods db export ./sdods-backup` first; `sdods db import ./sdods-backup` brings it back.

<Tabs items={['Installed', 'From a clone', 'Docker', 'Desktop app']}>
<Tab value="Installed">
Reset the users only:

```bash
sdods users reset --yes
```

Or reset everything the web UI stores:

```bash
sdods db reset --yes
```

`db reset` drops the database tables; run artifacts under `.sdods/runs/` stay on disk. For a truly
empty start, delete the whole state folder instead — it holds the database (`sdods.db` with its
`-wal` and `-shm` files), runs, leases and agent jobs, and is recreated on the next start:

```bash
rm -rf .sdods
```

Then start again and open the printed `/setup` link:

```bash
sdods serve --open
```

To reinstall the CLI itself, uninstall and install again. Your workspaces are not touched.

```bash
curl -fsSL https://sdods.com/install.sh | sh -s -- --uninstall --yes
```

```bash
curl -fsSL https://sdods.com/install.sh | sh
```

On Windows, in PowerShell:

```powershell
& ([scriptblock]::Create((irm https://sdods.com/install.ps1))) -Uninstall -Yes
```

```powershell
irm https://sdods.com/install.ps1 | iex
```

</Tab>
<Tab value="From a clone">
The same commands through the checkout's CLI:

```bash
bun run sdods users reset --yes
```

```bash
bun run sdods db reset --yes
```

```bash
bun run sdods serve --open
```

To reinstall from scratch, pull, reinstall dependencies and rebuild the UI bundle:

```bash
git pull && bun install && bun run web:build
```

</Tab>
<Tab value="Docker">
Everything the container stores lives in the `sdods-data` volume. Stop the container, remove the
volume, and start it again — the next start prints the `/setup` link in the container log:

```bash
docker volume rm sdods-data
```

```bash
docker run --rm -p 8080:8080 -v sdods-data:/data ghcr.io/yarlisaisolutions/sdods-server
```

To reset only the users, stop the container and run the CLI against the same volume — the image
passes any arguments other than `serve` straight to `sdods`:

```bash
docker run --rm -v sdods-data:/data ghcr.io/yarlisaisolutions/sdods-server users reset --yes
```

</Tab>
<Tab value="Desktop app">
Quit the app, then delete **both** its data folder and the workspace state. The data folder holds
the generated admin password and the workspace holds the database it belongs to. Deleting only the
data folder leaves an app that cannot sign in: it makes a new password the old database does not
know.

| OS      | App data folder                       | Workspace state              |
| ------- | ------------------------------------- | ---------------------------- |
| macOS   | `~/Library/Application Support/SDODS` | `~/SDODS/.sdods`             |
| Windows | `%LOCALAPPDATA%\SDODS`                | `%USERPROFILE%\SDODS\.sdods` |
| Linux   | `~/.config/SDODS`                     | `~/SDODS/.sdods`             |

On macOS, for example:

```bash
rm -rf ~/Library/Application\ Support/SDODS ~/SDODS/.sdods
```

Relaunch the app; it sets itself up again with a new admin password. To remove the app entirely,
delete it as you would any other application (or uninstall it with the package manager you
installed it from) and then delete the same two folders.

</Tab>
</Tabs>

<Callout type="warn">
  `sdods db reset` works on SQLite only. On Postgres (`DB_DRIVER=postgres`), drop and recreate the
  database yourself; `sdods users reset` works on both.
</Callout>

To regain access without resetting anyone else, set a new password instead. It signs that user out
everywhere, and `--activate` re-enables an account that was deactivated:

```bash
sdods users set-password admin --password '<at least 8 chars>' --activate
```

## Pages

| Page           | What it does                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| Dashboard      | pass-rate, duration and flaky trends; most-failing locators; latest runs; proposals inbox              |
| Projects       | the project YAML as a form: layers, browsers, tag policy, screenshot policy, integrations, MCP servers |
| Environments   | base URLs and non-secret settings; secret names shown with a presence indicator                        |
| Datasets       | upload CSV, JSON or YAML, preview the first rows, choose file or database storage                      |
| Runs           | filterable list, live log, scenario tree, step timeline with before/after comparison and API panels    |
| Feature editor | Gherkin editing with step completion from your project, lint diagnostics, run this scenario            |
| Recorder       | record a session as a pool user, save the spec, convert it with an agent                               |
| Agents         | start a role, watch it work, review the diff, accept or reject                                         |
| Integrations   | GitHub and Jira settings, connection tests, MCP servers the project consumes                           |
| Schedules      | cron builder with the next fire times, history, pause and resume                                       |
| Users          | create accounts, set platform roles and display names, deactivate                                      |
| Settings       | your profile, password and sessions, preferences, free scoped API tokens, MCP client install snippets  |

## Your account

The avatar at the foot of the sidebar opens the account menu: your profile, password and sessions,
preferences, API tokens and MCP clients, the admin pages when you are an admin, the theme (system,
light or dark) and Sign out.

| Settings tab        | What you can change                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------ |
| Profile             | display name and email; shows your username, platform role, memberships, last sign-in and when you joined    |
| Password & sessions | change your password (needs the current one); list signed-in browsers and sign out one of them or all others |
| Preferences         | theme, and the organization, workspace and project the app opens on (saved in this browser)                  |

| MCP clients         | the endpoint, its tools and install snippets for each client                                                 |

Changing your password signs you out of every other browser; the one you are using stays signed in.
These settings need a browser session: an API token cannot change a password or end sessions. With
authentication turned off there is no account to edit, so the Profile and Password & sessions tabs
are unavailable.

A platform role is changed by an admin on the Users page or with the CLI:

```bash
sdods users set-role <username> editor
```

## Roles

| Role   | Can                                                                           |
| ------ | ----------------------------------------------------------------------------- |
| viewer | read everything, download artifacts                                           |
| editor | start and stop runs, edit features and datasets, run agents, accept proposals |
| admin  | manage users, integrations, projects, tokens                                  |

Roles are per workspace: a user's effective role is the stronger of the explicit workspace membership and the one implied by the organization membership (`member` → viewer, `admin` and `owner` → admin). Platform admins are admin everywhere.

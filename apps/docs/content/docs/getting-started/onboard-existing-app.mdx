<Learn>
  How `sdods analyze` reads an application repository, what it detects and with what evidence, how
  to review the proposal before anything is written, which guess you almost always have to correct,
  and how to get from a clone to a passing suite in one sitting.
</Learn>

<Art
  scene="onboard-scan"
  caption="analyze reads the repository and reports what it found, with evidence. It writes nothing until you ask it to."
/>

Every command on this page was run against a real repository:
[cypress-io/cypress-realworld-app](https://github.com/cypress-io/cypress-realworld-app) — a React
and Express banking app with 33 existing Cypress specs. Clone it next to your SDODS checkout and
you can follow along exactly, or swap in your own app and read the same output shape.

```bash
git clone --depth 1 https://github.com/cypress-io/cypress-realworld-app.git ../cypress-realworld-app
```

## The five minutes

<Steps>
<Step>**Analyze** the repository. Nothing is written.</Step>
<Step>**Read** what it found, and how sure it is.</Step>
<Step>**Apply** the proposal into `projects/<slug>/`.</Step>
<Step>**Correct** the one or two guesses it could not make from the source.</Step>
<Step>**Run** it: the API layer passes immediately, and the UI layer tells you what needs a login.</Step>
</Steps>

## 1. Analyze

```bash
sdods analyze ../cypress-realworld-app
```

frameworks with a confidence score, the test-id attribute _counted_ in the source, the

## 2. Read the proposal

<Art
  scene="onboard-proposal"
  caption="The proposal is a document, not a commit. Everything in it is editable, and nothing is on disk yet."
/>

Below the analysis, `analyze` prints the project it would write: the slug, the layers, the
test-id attribute, the routes it will address by name, the tag taxonomy, and one module per route
group.

```yaml
# Generated by `sdods analyze`. Review routes, modules and auth before committing.
slug: rwa-bank
name: RWA Bank
layers: [ui, api, hybrid]
testIdAttribute: data-test
routes:
  signin: /signin
  signup: /signup
  personal: /personal
  contacts: /contacts
tags:
  suites: [smoke, regression, sanity]
  roles: [standard, admin]
```

Read three things before you apply it:

| Read this    | Because                                                                                |
| ------------ | -------------------------------------------------------------------------------------- |
| `routes`     | a catch-all route (`/*`) or a parameterised one may need a real path to be reachable   |
| `modules`    | they become your tag names and your folder names; rename them now, not after 200 tests |
| `envs/local` | base URLs are inferred from the source and are the guess most likely to be wrong       |

## 3. Apply

```bash
sdods analyze ../cypress-realworld-app --apply --project rwa-bank --name "RWA Bank"
```

<Art
  scene="onboard-apply"
  caption="--apply is the first write. It creates a project you own: plain YAML, plain Gherkin, plain TypeScript."
/>

```
projects/rwa-bank/
├── sdods.project.yaml          # layers, routes, modules, tags, test-id attribute
├── envs/local.yaml             # base URLs, headers, user pool size
├── features/                   # 14 starter features: one per route group, one per API group
│   ├── signin/signin.feature
│   └── login/login-api.feature
├── pages/HomePage.ts           # a page object to grow
├── steps/                      # fixtures, auth and project steps
├── data/common/users.csv       # the user pool, empty of secrets
├── har/  ·  recorded/          # ready for `sdods har record` and `sdods record`
└── README.md
```

The generated scenarios are health checks, not aspirations. A page scenario asserts the route
renders; an endpoint scenario asserts the endpoint answers with a non-5xx status inside five
seconds:

```gherkin
@ui @signin
Feature: Signin pages

  @smoke
  Scenario: The signin page loads
    Given I navigate to the "signin" page
    Then the page URL should contain "/signin"
```

Lint them straight away — it is instant, and it is the difference between a typo now and a red
suite in ten minutes:

```bash
sdods lint -p rwa-bank
# ✔ 14 feature file(s) linted, no findings
```

## 4. Correct the guesses

Static analysis reads what the source says, and a running application sometimes disagrees. On this
repository five things needed a human, and each one is a single line:

| The guess                                    | The correction                                                                                                                     |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| API base URL `http://localhost:3000`         | the backend listens on `3001`; only the frontend port is obvious from `.env`                                                       |
| Login selectors `[data-test="username"]`     | the app spells them `signin-username` — and the attribute is on the Material UI wrapper, so the selector needs a trailing ` input` |
| Routes `/*` and `/(public)?`                 | router patterns, not addresses; delete them and their generated modules                                                            |
| Route `/implicit/callback`                   | only exists when the app runs in its Okta mode                                                                                     |
| `steps/auth.ts` exporting `strategy: 'none'` | the app has a form login: `strategy: 'form'`                                                                                       |

```yaml title="projects/rwa-bank/envs/local.yaml"
api:
  baseUrl: http://localhost:3001 # analyze guessed 3000; the backend listens on 3001
```

```yaml title="projects/rwa-bank/sdods.project.yaml"
auth:
  strategy: form
  storageState: true
  form:
    loginPath: /signin
    usernameSelector: '[data-test="signin-username"] input'
    passwordSelector: '[data-test="signin-password"] input'
    submitSelector: '[data-test="signin-submit"]'
    readyUrl: /
```

<Callout type="warn">
  Expect exactly this kind of correction on any real application. The analyzer is deliberately
  literal: it reports what the files say and marks how sure it is, rather than inventing a plausible
  configuration you would then have to unpick.
</Callout>

## 5. First run

Start the application, then run the two layers.

```bash
# terminal 1 — the application under test
cd ../cypress-realworld-app && yarn dev

# terminal 2 — SDODS
sdods run -p rwa-bank -e local -l api                        # endpoints, no browser
sdods run -p rwa-bank -e local -l ui -b chromium -t @smoke   # pages, in chromium
```

## What the suite covers, and what it does not

```bash
sdods coverage -p rwa-bank --routes
```

`coverage` joins the route and endpoint inventory with the scenarios you have, split by suite tag,
so the gap is a number rather than a feeling.

```
Coverage for rwa-bank
routes 4/4  endpoints 9/9  roles 0/2  scenarios 13  @smoke=13
```

Everything answers, and nothing is yet checked as a particular person: `roles 0/2` is the whole
story of a freshly onboarded project.

<Art
  scene="onboard-coverage"
  caption="Reachability is covered on day one. Roles and regression depth are the work you choose next."
/>

The generated suite gets you to “everything answers”. The next three things are worth doing in
this order: a real assertion per role, `@regression` scenarios for the flows that make money, and
data that comes from a fixture rather than from whatever the database happens to hold.
[The workshop](/docs/workshop/) walks all three on this same repository.

## Bringing existing tests along

`analyze` copies existing Playwright specs into `recorded/imported/` unless you pass
`--no-import-specs`. Cypress specs are inventoried rather than copied, because their API differs —
the migration path is to record the flow once and convert it:

```bash
sdods record -p rwa-bank -e local --url signin --name signin-flow
sdods record convert projects/rwa-bank/recorded/signin-flow.spec.ts
```

`record convert` asks your configured model adapter to turn the recording into a **proposal**: a
feature file plus the steps it needs, using role and test-id locators instead of the CSS chains the
old specs relied on. Nothing is applied automatically — you review it with `sdods proposals list`
and accept it when you agree. Without a model key, `--dry-run` prints the plan and
`--adapter fake` produces the shape. [Guides → Migrating](/docs/guides/migrating/)
covers the whole path.

## Start from scratch instead

When there is no application to read — a service that does not exist yet, or a repository you
cannot clone — `project create` scaffolds the same shape by hand:

```bash
sdods project create my-app \
  --ui-url http://localhost:3000 \
  --api-url http://localhost:3000/api \
  --env local
```

It writes the YAML, an environment, fixtures, an authentication stub, a page object, health
features and a data folder. See the [project command reference](/docs/reference/cli-commands/project/).

## What analyze detects

| Area            | Detected                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| Package manager | npm, pnpm, yarn, bun; monorepo shape                                                                            |
| Frontend        | React, Next.js, Vue, Nuxt, Angular, Svelte, plain                                                               |
| Routes          | Next.js `app/` and `pages/`, React Router, Vue Router, Angular, Express, Fastify, NestJS, Spring, Flask, Django |
| API contracts   | OpenAPI or Swagger on disk, or at the usual URLs                                                                |
| Locators        | the test-id attribute in use (`data-testid`, `data-test`, `data-cy`, `data-qa`), by counting                    |
| Existing tests  | Playwright, Cypress, Cucumber, Jest — with a breakdown of their locator styles                                  |
| Authentication  | login pages and auth libraries (passport, Auth0, Okta, Cognito, NextAuth …)                                     |
| Environment     | `.env` files, base URLs, Docker Compose ports, CI provider, locales, accessibility tooling                      |

<Learn>
  The gaps that exist in the current release, why they exist, and what to do in the meantime.
</Learn>

| Area                   | Limitation                                                                                                                                                                                                                                                                                                           | Workaround                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Visual baselines       | Baselines are stored per run target **and platform** (`features/__screenshots__/<run target>/<platform>/`). The demo ships only `darwin` baselines, so `@visual` fails in the nightly Linux run until the `visual-baselines` workflow's pull request is merged.                                                      | Run the `visual-baselines` workflow, review its pull request of `linux/` PNGs and merge it.                             |
| Feature editor         | Step completions come from the project's step catalogue; the `@cucumber/language-service` WebAssembly is loaded best-effort and may be unavailable, so semantic diagnostics fall back to the parser and server lint.                                                                                                 | Diagnostics from `Save` and `Validate` are authoritative.                                                               |
| Process gates          | `sdods run --process` does not evaluate gates on one shard of a sharded run (`--shard i/n`), because a shard is not the whole run. A run started from the CLI and ingested straight into the database keeps its gate verdict in `gates.json` only; the server records it on the run when the server started the run. | Gate the unsharded run, or read `gates.json` / `summary.json` from each run directory.                                  |
| `@a11y` scope          | The tag audits the page the scenario ends on, not every page it visited.                                                                                                                                                                                                                                             | Add `the page should have no accessibility violations of impact "serious" or worse` after each navigation that matters. |
| Third-party demo sites | The demo project targets public sandboxes (SauceDemo, JSONPlaceholder). Their session cookies live ten minutes; SDODS refreshes cached login state automatically when cookies expire.                                                                                                                                | Use `--har-replay --strict` for fully offline runs.                                                                     |
| Load testing           | `sdods load` drives HTTP requests listed in a profile; it does not replay `@api` scenarios or browser flows, load runs are not recorded in the results database, and an OAuth client-credentials token is minted once per run and not refreshed.                                                                     | Keep profiles shorter than the token lifetime; read `summary.json` in the run directory.                                |
